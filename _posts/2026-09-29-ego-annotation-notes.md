## 一段话版本

第一视角视频记录了大量真实、自然的人类操作——做饭、整理、使用工具。我们的管线把这类视频变成机器人可以直接学习的逐帧标注：每只手 21 个关键点的世界坐标、相机的世界位姿、物体的三维状态，以及逐帧的操作语义描述。方法上的核心判断是：**标注质量取决于手物交互与物理一致性有没有被正确建模**，所以我们先用「可见性、接触、时序、非穿透」这些物理约束把手物联合状态做到物理上可信；质量站住之后，再把它工程化成多视频共享算力的高吞吐生产管线，最终以 API 形式对外交付——单目或双目 RGB 视频进去，一份结构化 JSON 出来。

## 背景：机器人学做菜，需要一份「有物理常识的教案」

先用非专业的方式解释一下我们在做什么。

让机器人学会人类的手上功夫，最直接的教材就是人类自己的操作视频。但一段「手拿起牛奶盒倒进杯子」的视频，机器人是看不懂的——它需要有人把这段视频翻译成精确的数学语言：每一帧里，手在三维空间的哪里？每个指关节的坐标是多少？相机自己移动到了什么位置？牛奶盒的位姿怎么变？手和盒子什么时候接触、什么时候松开？

这个「翻译」工作就是标注。它难在两件事：

1. **要可信**。随手拼起来的标注可以看起来很连贯，但手部和物体在物理上互相穿模、深度和尺度对不上、动作和物体运动的因果关系断裂——机器人学了这种标注，就像学生背了一份本身就有错的答案。
2. **要规模**。训练数据规模决定覆盖面，几百条视频训不出通用能力，需要的是几百、几千小时。

这两个目标有张力：追求质量的研究管线往往慢得离谱（我们后文会看到「1 秒视频要算 4 分钟」的阶段），而追求规模又容易牺牲质量。这篇文章记录的，就是我们如何先解决质量、再解决规模的全过程。

## 客户合作：目标与最终交付

客户方有规模化的一视角数据生产线（每周产出约一万小时生数据），但缺一条能把原始视频变成三维标注的处理管线；我们有算法和算力。合作的工程目标由此非常清晰：**把我方处理量级从「每月一万小时」提升到「每周一万小时」**，精度要求到标称 5 毫米量级，合作模式是数据交换——对方数据给我方标注，标注结果返还，我方可自用。

第一个落地里程碑是 **30 小时 pilot 数据的完整交付**，验收物包括四类：

- 头部位姿轨迹（相机在三维世界里怎么动）；
- 手腕位姿与关节位置轨迹（两只手每根手指怎么动）；
- 精细视频切分（把连续长视频切成语义完整的片段）；
- captioning 结果（每段片段的自然语言描述）。

合作推进的节奏大致是：6 月底内部立项并跑通第一个 demo → 7 月初确立合作与 API 化方向 → 7 月中下旬 30hr pilot 进入 P0、管线两轮重构 → 8 月 A800 迁 H200、对外 API 试运行 → 9 月批量交付与研究线（手物交互优化、Cosmos 微调）并行。后文按这条时间线展开。

## 我们交付什么：一份 JSON 里的四类信息

对使用者来说，整条管线封装成一个 API：注册账号、生成 Key，然后三步走——

```bash
# 1. 上传视频
curl -X POST https://<endpoint>/api/v1/annotations \
  -H "Authorization: Bearer $DEXGEM_API_KEY" \
  -H "Content-Type: video/mp4" \
  -H "Idempotency-Key: <uuid>" \
  --data-binary @./kitchen-task-01.mp4

# 2. 轮询任务状态直到 succeeded
curl https://<endpoint>/api/v1/annotation-jobs/<JOB_ID>

# 3. 下载结果
curl https://<endpoint>/api/v1/annotation-jobs/<JOB_ID>/result > annotation.json
```

返回的 `annotation.json` 包含四块内容：

| 内容 | 说明 | 给非专业读者的类比 |
|---|---|---|
| 手型参数 | 每只手的大小、逐指长度、掌宽、指节间距（左右手分开输出） | 量出了这双手的「尺码」 |
| 手部 21 关键点 | 每帧每手 21 个关节点的**世界坐标**（米制） | 每一瞬间手指骨骼的精确位置 |
| 相机世界位姿 | 每帧相机的 6DoF 位姿 | 「这只眼睛」在空间中的运动轨迹 |
| 逐帧语义描述 | 分段自然语言字幕 + 接触状态判断 | 自动写出来的操作解说词 |

## 质量方法：把手物接触当成状态估计问题

这是整条管线的方法论核心，也是团队博客准备重点讲的部分，这里用我自己的话复述一遍。

**核心立场：视频里真正想要的，是整段操作中手和物体的联合状态；而每个单独的感知模型只能给出这个状态的一个带噪声的侧面。** 手部检测、手部姿态、相机运动（SLAM）、物体可见表面、分割——它们各自会在不同场景下出错，还经常互相矛盾（比如手部模型自带的深度和单目深度估计的尺度不一致，后文会讲到这个真实的坑）。所以管线的任务不是「把模型输出拼在一起」，而是**在互相矛盾、各有盲区的证据之间，找一个既符合观测、又符合物理直觉的解释**。

整条方法链可以画成一张图：

![标注流程：观测证据 → 硬约束/软约束门控 → 鲁棒优化 → 解空间](/assets/ego/pipeline_flow.png)

四个关键设计，每一条都值得单独说：

**1. 观测是带不确定度的证据，不是真值。** 每条观测都带着来源和置信度进入后续环节。如果其中任何一个模型可靠到能单独决定答案，这条一致性管线就没有存在的必要。

**2. 解空间是显式的，允许「未知」。** 当前观测支撑不了的状态，保留为显式的不确定假设，而不是因为某个结果「看起来完整」就填成确定值。对应到服务实现里，`n_hands=0`（这帧没检测到手）是一个**合法的成功产品**，不统计为失败——宁可少，不可错。

**3. 约束层分硬软两级，并决定什么证据有资格生效。** 硬约束做「准入判断」（哪些观测此刻可信、哪些几何真的被看见了）；软约束把物理常识表达成代价——运动应当连续、遮挡关系应当一致、**物体表面不可穿透**。手物 mesh 的交叉区域被优化限制到合理范围，它在物体表面的投影恰好就是接触面：

<video controls preload="metadata" src="/assets/ego/milk_overlay_interpenetration.mp4" style="width:100%"></video>

红色区域即优化后仍存在的少量手物交叉区域，其投影代表接触面。

**4. 优化按证据的依赖关系推进。** 先确定被观测支撑最充分的状态（比如被稳定看到的物体表面），再用它约束更不确定的部分（被遮挡的手指、接触关系），让可靠的证据引导不可靠的部分。

手与物体之间的物理一致性约束直接落到求解器里——下图是约束分析的可视化，手物之间保留约 2.0mm 的间隙阈值：

![手部与物体物理一致性约束分析（间隙 2.0mm）](/assets/ego/physical_constraint.png)

### 精度：公开基准上的数字

在 HOT3D 公开基准上与主流方法对比（手部姿态，PA-MPJPE 口径注意与未对齐 MPJPE 不可直接比较）：

| 方法 | HOT3D 手部误差 |
|---|---|
| Dyn-HaMR | PA-MPJPE 8.87 / G-MPJPE 42.36 |
| HaWoR | PA-MPJPE 4.79 |
| **ours** | **MPJPE 8.35，PCK_AUC 83.31%，指尖 PCK_AUC 81.37%，MPVPE 2.78mm** |

在世界系相机轨迹评测上，我们的短板很诚实：HOT3D 上 ATE 均值 305mm（对比 DROID-SLAM 49.1、MegaSaM 94.4），但**完成率 100%**——竞品方法在困难片段上会直接放弃，我们会给出带不确定度的结果。在手物交互更贴近的评测上差距更小：合作方数据的人工对比里，我们左手误差 4.7–6.5mm、右手 6.2–7.6mm，而基线方法 15.5–35.9mm，**好约 3–7 倍**。

## 失败边界：「你永远无法把垃圾变成金子」

比成功案例更有价值的是失败边界。两个典型：

**失败一：物体观测噪声太大。** 下面的例子里优化后物体仍有明显抖动——原始观测证据质量太差，优化只能减少误差、不能凭空创造信息。团队的原话是：「观测证据来源，是标注的最重要来源。**你永远无法把垃圾变成金子。**」

**失败二：背景特征过少导致相机轨迹崩坏。** 输入视频对着一面纯白桌面，SLAM 提不出可靠特征，相机位姿完全是噪声（下图右侧的杂乱轨迹）：

![失败案例：背景特征过少导致相机位姿噪声极大](/assets/ego/failure_camera.png)

这两个失败共同指向一条结论：**观测误差不可避免，但通过合理的手物交互物理约束建模，我们仍能绕过它的一部分影响**——因为操作的目标是让物体按期望的方式移动，手物交互状态在因果链上比单纯的手部标注更靠近「最终结果」，是更值得投入保证质量的可学习信号。

## 研究管线 V1：17 个模块的 Harness DAG

方法站住之后，第一版工程化是一个单视频闭环的「研究管线」，按模块拆成 M00–M16 共 17 个阶段：输入与时间线 → 深度/相机候选（DepthPro、UniDepth、DROID、VGGT 等多路）→ 手部候选（RTMLib、WiLoR、HaMER、HaWoR）→ 公制 MANO → 目标物体规划（OWLv2 检测）→ 分割（SAM2）→ 可见表面 → mesh 候选 → 刚体位姿拟合 → 接触/遮挡/非穿透约束 → 状态组装 → 渲染 → 基准评测。

几个当时就定下的设计原则，后来一直延续：

- **候选注册表 + agent 判决**：每个模块生成多个候选，注册表比较打分，agent 节点做 sanity 判断。这个设计后来被证明太重（V1 实测「agent 时常 error 导致速度慢」），但「多候选、可替换」的思想保留了下来。
- **GT 防泄漏**：评测模块里有专门的 `gt_leakage_guard` 步骤——预测阶段绝不读取真值，真值只在结果冻结后用于评测。这条纪律让所有公开基准数字都经得起复算。
- **版本兼容显式化**：V18/V19/V20 的 legacy 逻辑全部走 adapter，职责边界写死在模块名里。

V1 最大的结构性问题写在它自己的文档里：批量与并行控制面整章 7 个步骤全部标注 `missing/design-only`——**单视频闭环再好，也吃不下规模化的订单**。这就是 V2 的动机。

## 转折点：砍掉 SAM2，3.3 倍从哪里来

吞吐调优的第一刀不是加机器，而是减模型。

压测发现手部检测环节（YOLO + SAM2）是最大瓶颈，而 SAM2 的逐帧 mask 精细分割对下游的帮助有限。决策：**手部检测改 YOLO-only，彻底移除 SAM2**，mask 信号不再输出，可见性统一置 1.0（缺失槽位记 `unresolved`）。关键约束是**下游 payload 完全不变**——WiLoR、HaWoR、DROID 的调用契约原样保留，接口不变、只换 backend。

一刀下去的数字：

| 指标 | SAM2 版 | YOLO-only | 提升 |
|---|---|---|---|
| 单请求延迟 | ~265ms | ~81ms | 3.3× |
| 16 req/s 下 p95 | 1.28s | 0.13s | 9.9× |
| 稳态吞吐 | ~4 req/s | ~16 req/s | 4× |
| 显存（检测+WiLoR） | — | 3995 MiB | — |

代价是放弃了 mask 质量信号（不确定性改由独立字段表达）。这是全项目性价比最高的一次取舍：**吞吐问题先用「减法」解决，再考虑「加法」**。

## V2：Ray Serve 分卡与压测方法论

V2 把管线改造成 Ray Serve 微服务：每块物理 GPU 一个独立 Ray 集群，GPU 排他性由进程级 `CUDA_VISIBLE_DEVICES` 在 `ray start` 之前保证，而不是靠自定义调度标签——文档原话是「不会出现自定义标签假隔离」。6 个部署组、7 个端点的拓扑：

| GPU | 端点 | Python/Torch |
|---|---|---|
| 0 | UniDepth（单目度量深度） | 3.11 / 2.7.1+cu126 |
| 1 | Hands 检测 | 3.10 / 2.0.1+cu117 |
| 2 | DROID（SLAM，有状态会话） | 3.10 / 1.13.0+cu117 |
| 3 | HaWoR + Infiller（共卡） | 3.10 / 1.13.0+cu117 |
| 4 | WiLoR（手部重建，V2 新增独占） | — |
| 6 | Cosmos3（语义描述） | 3.13 / 2.10.0+cu128 |

分卡的直接收益：WiLoR 从与检测共卡时的 8–9.5 req/s 提升到独占 16–20.8 crops/s。

### 压测量纲陷阱：一个容易自欺的细节

V2 文档里我最欣赏的一段，是对「压测数字怎么换算」的较真。团队发现，只有深度/检测/SLAM 这类端点满足「1 请求 = 1 源帧」，可以直接 `req/s ÷ 360` 换算成「视频帧/秒」；而：

- WiLoR 的一个请求是**一只手 crop**（每帧可能有 0~2 只手），直接除会**高估 D̄ 倍**；
- HaWoR 的一个请求是 **16 帧 chunk**（stride 8、50% 重叠），除以 360 会**低估约 4 倍**；
- Infiller 是 **120 帧双手窗口**，低估 6 倍以上；
- Cosmos3 处理的是抽样帧 + 文本，「图像/秒」这个量纲对它根本不成立。

结论写成了方法论：**压测数字如果不定义 native 工作单元（1 帧 / 1 crop / 1 chunk / 1 window），就是有量纲错误的**；扇出常数必须取自真实管线 trace，不能拍脑袋。配套的还有两条测量纪律：单进程压测客户端会因 I/O 饥饿把服务「测小」（我们真的因此作废过一次 WiLoR 压测结果，保留为 invalid 历史记录）；open-loop + 每请求唯一内容哈希，避免缓存虚高。

### 全量批处理：1757 条的运营契约

客户 30h 数据集的全量批处理脚本有明确的运营守则：客户端并发 128、对 429 做 5 次退避重试（1/2/4/8/16s）、每 30 秒记录吞吐与 GPU 利用率、必须在 tmux 里跑。其中一条写得很硬：**「绝不伪造 masks（不返回零 mask 或假 mask）」**——宁可这条失败，不可交付假数据。

## 三次事故复盘

生产化的过程跌过三个值得写下来的坑。

### 事故一：22.6TB 的日志自尾随

旧启动器把服务 stdout `O_APPEND` 到 `gpuN.log`，又在同一个文件上跑 `tail -f` 做监控——tail 读到的内容又被写回同一文件，形成正反馈回路。发现时 GPU0 的日志已经 **~930GB**，GPU3 达到 **~22.6TB**，增速 2.3–7.2 GB/10s。

更精彩的是修复动作本身差点变成第二起事故：直接 kill tail 进程导致 session leader 退出，终端 hangup 沿进程组传播到了共享的 Ray 服务进程，两个推理端点当场不可达——原文总结得很到位：「证实了『tail 非 Ray 进程即安全』这一假设的错误」。

最终方案是把 owner / guard / observer 三种角色拆成独立进程组：owner 只写不读；guard 守护进程每秒轮询，超过 64MiB 就用 `flock` + 同 inode `ftruncate` 原地压缩（不 rename、不 unlink，避免 GPFS 上的悬挂 I/O）；observer 只通过 PTY 读。恢复后文件系统空闲空间从 ~40TB 回到 ~61TB。

### 事故二：一个环境变量引发的 NaN

DROID（SLAM 服务）曾把并发 batch 参数 `max_concurrent_ba` 提到 3 来提速，结果服务端全线 503。根因排查链非常教科书：该参数会让会话计算被调度到**非阻塞的旁路 CUDA stream**，而 DROID 及其依赖 lietorch 的自定义 CUDA kernel——经全量源码扫描证实——**零 stream 引用，只能在默认流上正确执行**（全库唯一命中的 "stream" 是 `#include <iostream>`）。旁路流与默认流竞态 → warmup 阶段位姿/深度即为 NaN → 归一化放大 → finalize 失败。

修复「不改一行代码」：六端点统一回 `BA=1`，并用 256 帧 P0 gate（输出全部有限、`nonfinite_count=0`）在六个端点上验证通过。吞吐缺口改用横向扩容补（见 V3）。这条后来被写进文档的最高操作规则：**`max_concurrent_ba` 必须保持 1**，同时留了一条运维红线——历史环境变量可能残留在 Ray head/proxy 进程里，有效值必须以实际 ServeReplica 进程的 `/proc/<pid>/environ` 为准。

### 事故三：HaWoR 返回全零顶点

HaWoR（手部重建）输出中 mesh 顶点全是零，但关节点一直正确。诊断很巧：顶点和关节来自**同一次** MANO 前向计算，关节全对说明模型没问题——问题出在上游代码只把 `joints` 放进了输出字典，把 `vertices` 丢了，serving 层静默补了零。

修复后策略升级为 **FAIL CLOSED**：缺失、形状错、含非有限值的顶点直接报 `MODEL_FAILURE`，绝不静默零填充。这与「绝不伪造 masks」是同一条产品哲学：**数据服务里，诚实的失败好过漂亮的伪造。** 修复后的线上验证：vertices (16,778,3) 共 37344/37344 全部非零，J-regressor MAE 2.96mm。

## V3：CUDA IPC 与一卡六端点

DROID 成为瓶颈后，V3 不再加卡，而是把**单卡内部榨干**：GPU2/GPU7 各跑 3 个 DROID 副本（共 6 个独立端点、每端点 8 会话、合计 48 并发会话），同卡三副本通过 **CUDA IPC 共享同一份权重显存**——先启动的副本是 owner，持有 CUDA context 与权重；后启动的从 handle 文件 reconstruct，绕过 Python GIL 的吞吐限制。

这套机制带来一条新的「咒语」：**杀掉 owner = handle 失效 = 该卡所有副本悬空**。所以重建必须 owner-first（先删 importer、再删 owner、归档失效 handle 留证、新 owner 重建、importer 逐个恢复）。配套的会话粘滞用 SQLite WAL 实现跨进程的 lease 记账（TTL + exact-once release），保证一个视频的 256 帧全部送到同一个端点。

V3 的 DROID 单卡成绩：**15.33 fps/GPU**（1024 帧序列、3 并发、IPC 共享权重、每副本 8 会话）。另一条隐藏收益是双目替代单目的验证：接入双目后内参/外参估计误差约 1%，UniDepth 这个曾经的头号瓶颈可以从关键路径上拿掉。

## 最终形态：maestro（Hatchet DAG）× ego-compute

2026 年 8 月底，架构重写为两个仓库的分工：

- **ego-maestro**：Hatchet DAG 编排，**零计算**——只负责调度；
- **ego-compute**：4 个按 Python ABI 划分的 Ray cluster，承载 HTTP GPU 服务与 CPU actor。

为什么按 Python ABI 划分？因为 DROID 的编译扩展绑定 CUDA 11 与特定 RPATH，Cosmos3 需要 Python 3.13——**模型依赖决定了环境边界，环境边界决定了集群边界**，这是多模型服务化绕不开的物理约束。

数据面上有一条值得所有多阶段管线借鉴的约定：

> **大 tensor 一律落盘 `artifacts/<job>/`，调度边只携带小 JSON 和磁盘路径。**

十个节点的职责与依赖如下（HTTP 服务节点与 Ray CPU actor 混排，深度/检测/语义三个无依赖节点并行起跑）：

```
N1 解码(CPU) ──┬─→ N2 UniDepth 深度 ──────┐
               ├─→ N3 手部检测 ─┬─→ N4 WiLoR MANO ─┐
               │               └─→ N5 DROID SLAM ←─ 内参 slot
               └─→ N8 Cosmos3 语义
N4 + N5 + N2 + N3 ──→ N6 融合(CPU, 世界系双手时间线)
N6 + N8 + N2 ──→ N9 渲染(overlay.rrd + annotation.json v3)
             └─→ N10 打包(可选)
```

整条链路的 infra 分层：

![工程管线 infra 总体结构：Web 层 → 编排层 DAG → 计算层工作区](/assets/ego/infra_layers.png)

这种拆法的意义不止于并行：质量控制、错误重试、状态追踪、资源扩容都发生在**稳定的模块边界**上——某个观测模型升级或横向扩容，前端接口、任务队列和最终 schema 都不用动；失败被记录为可观察的状态（intake / inference / fusion / rendering 四类），多条请求并发时能快速定位问题在哪一层。

## 吞吐演进：从 4 fps 到 20 视频小时/小时

把全篇的吞吐数字串成一条线（口径见上文量纲讨论）：

| 阶段 | 端到端吞吐 | 瓶颈 | 解法 |
|---|---|---|---|
| V1 agent 编排 | 一个下午 16 条 | agent 频繁 error、模型串行 | 转向服务化 |
| 服务化初期 | 4 fps（视频帧） | UniDepth | —— |
| 砍 SAM2 后 | 16–20 fps | DROID | YOLO-only |
| V2 全量批处理 | 6 视频/小时 | DROID 长视频客户端 bug | 修 bug |
| V3 CUDA IPC | 15.33 fps/GPU × 多卡 | —— | 六端点 + 权重共享 |
| 目标形态 | **~100 fps ≈ 20 视频小时/墙钟小时**（单 H200 节点、双目替代 UniDepth、降帧率） | —— | —— |

这条线的每一格都对应一次架构决策，回头看，「减模型」和「换拓扑」的贡献远大于「调参数」。

## 对外 API 的真实考验

技术闭环不等于产品闭环。8 月初 API 上线前后的几个真实片段：

- **138 字节的响应**：测试同事 curl 上传后秒回 138 字节，排查半天——命令里少了个 `@`，传上去的只是文件名。第一课：用户的第一条 curl 命令必须写在文档最显眼的位置。
- **「意义不明的错误信息」**：负责人亲自当用户提交视频，收到无法理解的报错，当天的结论是「现在算法和 infra 层面就 alpha demo 来说都没大问题，但是**用户完全无法使用**」，验收标准被定为：把文档扔给 AI agent、不加任何上下文，能直接跑通全流程。
- **压缩包之争**：早期结果打包成 zip 下载，理由是「看不懂哪些是中间结果」；产品视角的反驳是这「违背了做 API 的初衷」。最终契约收敛为：**payload 直接返回 JSON，去掉视频和中间产物**，渲染交给用户侧脚本。
- **caption 粒度**：从逐帧字幕改为 `(start_time, end_time, caption)` 分段元组——下游用户要的是片段，不是帧。
- **SLA**：生产环境承诺工作时间 60 分钟内处理完客户请求。

这一段的教训浓缩成一句话：**API 的难度不在吞吐，在于「陌生的用户拿着错误的输入也能得到体面的错误信息」。**

## 客户动捕 GT：432 条拍摄方案

标注质量要验证，就需要比标注更准的真值（GT）。方案是光学动捕 + 第一视角设备同采：约 3m×3m×3m 空间，头戴双目设备（下图为设备实拍——黑色双摄模块固定在帽檐上），3 名测试人员覆盖不同身高与手型。

![客户头戴双目设备实拍](/assets/ego/head_device.png)

拍摄方案的设计比想象中讲究：

- **任务分三层**：简单（20–40s：拿放、换手、拧瓶盖）、中等（1–2min：叠衣服、分类、折纸）、困难（3–5min：完整衣物整理、拆箱上架），任何任务不超过 5 分钟；
- **专项变量隔离**：镜头轨迹（纯转头/平移/组合运动）、光照（正常/暗光/侧光/强光）、遮挡（双手互遮/物体遮手/短时完全遮挡 1–2s），每类只取 1–2 条专项，其余让真实任务自然产生；
- **动作规范**：每条开头结尾手部平放静止 3 秒（给时间对齐留锚点）；
- **设备组合**：红外 + 光惯、光惯 + 头戴等四种组合，每人 144 条，总计 **432 条**，编号规则 `MC序号-人员-任务-条件-采集-头戴-复拍`。

过程中还沉淀了一份「对设备方的数据需求清单」，核心六项：三类轨迹、动捕原始时间戳与实际帧率、**视频/IMU/动捕的时间同步方案**、每条起止同步信号、动捕坐标系与相机坐标系的外参、标称精度声明。这份清单的本质是：**跨系统 GT 的可信度，取决于时间同步与外参这两个接口是否在拍摄前就书面确定**。实践中的坑也在这里——贴标记点麻烦、红外相机与光惯手套不适配、数据线材损坏重采，都是「接口没先约定」的代价。

## 验收哲学：买方不需要信任供应方

数据交付怎么验收？团队把验收设计成了一套「信任最小化」的证据链，原文金句：「**买方不需要信任供应方结论，可以按以下证据验收。**」

1. **视觉重投影审计**：交付演示视频是无标签干净版，接触/近接触、可见性、置信度层级渲染在独立 QC 版本里，肉眼可查；
2. **无真值批量指标**：用独立的手部检测器算重投影残差、独立的分割器算 mask IoU，加上深度残差、时间抖动、手物穿透体积六件套；
3. **公开基准复跑**：所有基准数字由交付的 `repro.sh` 从冻结预测复算，预测阶段从未读过真值；
4. **分层人工抽检**：每 1000 条抽 20 条，按置信度层级/物体尺寸/遮挡程度/动作类型分层抽样；
5. **置信度排序测试**：Tier A 必须显著优于 B/C，未解析状态不作为训练目标；
6. **一日验收测试**：20 条分层片段，看并排视频 + 核对质量报告 + 复跑公开基准，三类证据一致才整批接受。

这套设计后来同样用在我们对外的 API 交付上——把「质量」从一句承诺变成一组可复算的证据，是数据服务区别于普通软件交付的关键。

## 沉淀下来的原则

把整个项目翻下来，能反复被验证的原则有这几条：

1. **质量先行，规模殿后**：先用物理约束把单条标注做到可信，再工程化摊薄成本；两部分共享同一份原始证据。
2. **吞吐问题先做减法**：砍 SAM2 的 4 倍收益大于任何调参。
3. **观测是证据不是真值**：所有感知输出带置信度进入融合，支撑不了的保留显式未知。
4. **绝不伪造**：不返回假 mask、不静默零填充、FAIL CLOSED。
5. **不做 fallback**：任何环节失败就显式失败并记录状态，静默降级是数据质量的头号敌人。
6. **压测先定义量纲**：不定义 native 工作单元的吞吐数字是自欺。
7. **正确性 gate 与吞吐指标分开**：256 帧有限性验证不是性能数据，两者在文档里永不混报。
8. **运维留证**：失效的 CUDA IPC handle 要归档、作废的压测要保留 invalid 记录、回滚手册先于 cutover 写好。
9. **用户视角验收**：文档 + 错误信息 + 契约设计，让「陌生用户 + AI agent」零上下文跑通才算交付。

## 还没解决的问题

诚实记录当前遗留：

- **腕部表征**：训练集右腕误差 21.8–22.3mm，但未见任务的左腕中位误差 52–60mm。逐帧腕滤波能把 21 点运动残差从 8.7 降到 7.6mm，却不改善相机系位置误差——说明问题在表征方式（应预测相机坐标系下的每帧姿态），而不是平滑不够。
- **研究管线的速度**：带完整物理约束优化的研究版本仍是「1 秒视频算 4 分钟」，与生产管线的速度差两个数量级，优化模块（RL 微调接触/位姿）还在迭代——milk 案例的尾帧误差已从 67mm 降到 28mm，但旋转还有差距。
- **语义标注的稳定性**：视觉语言模型输出的结构化 caption 偶发不合规导致管线失败，结构化输出的约束仍在加固；左右眼分开标注时语义描述可能不一致。
- **吞吐的最后一公里**：距离「每周一万小时」的目标还有距离，推理下探到廉价卡（4090 级）的方案在评估中。
