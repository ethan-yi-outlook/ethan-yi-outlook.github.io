## 前言

具身智能的软件栈和纯软件栈有个根本区别：**它的上游是物理世界**。数据来自真机动捕、来自穿戴设备、来自第一视角视频；下游也是物理世界，策略要跑在真机上、要在毫米级容错范围内完成接触操作。中间夹着的一整套采集、标注、训练、部署、评估基础设施，才是决定迭代速度的真正变量。

这篇笔记记录 DexGEM（高灵巧双臂手具身智能系统）软件栈的架构、参数与踩坑。核心是一条**「采集 → 标注 → 训练 → 部署 → 评估 → 反馈」的数据飞轮**，以及支撑它的一整套自建基础设施。

> 本文为个人技术复盘笔记。已隐去全部人员姓名，并对合作方 / 服务商信息做泛化处理；技术参数、架构设计与故障分析保持原值。

## 一、全景：五层闭环

```
数据采集 ──▶ Ego 标注 ──▶ 模型训练 ──▶ 真机部署 ──▶ 评估基准

  遥操作框架          手部 6DoF MANO       Tenon 训练基建     RTC 33ms chunk      Dexathlon 任务集
  光学/光惯动捕        UniDepth / DROID    Pi0.5 VLA 微调     teacher-student     LIBERO 每日回归
  Lance 格式入库       Cosmos 语义标注     小模型 RL          sim2real 三级处理    (物体×手势) 成功率
         │                                                          │
         └──────────────── 评估结果反哺采集任务设计 ◀────────────────┘
```

底座：自建 H200 双节点 · 自研 GPU 调度平台 · NAS + 对象存储 · LLM 网关 · 监控与机器人治理。

三个贯穿全局的设计原则：

- **群组即模块**：每个技术方向一个独立协作群（模型部署 / 训练基建 / VLA / RL / 触觉映射…），讨论记录即技术决策日志。
- **双模型路线并行**：大模型 VLA（负责泛化能力）与小模型 RL（负责真机可靠性）双线推进，最终融合为一条管线。
- **基建先行**：算力调度、存储、网关、监控全部自研自建——**infra 的效率和可靠性是生命线**。

### 关键量化指标（截至 2026-09）

| 指标 | 数值 | 含义 |
|---|---|---|
| 算力 | H200 双节点（8 卡 × 2） | 自建托管 |
| 存储 | 自建 NAS **0.5 PB** | 32 × 16 TB ZFS |
| 采集规模 | **33,213 条轨迹 / 96.6 小时** | 累计（3 个 namespace，713 个任务） |
| 采集产能 | **~850 条/日** | 在线设备 4 台 |
| 标注吞吐 | UniDepth **40 fps**（2×A800 优化后） | 深度估计 |
| 标注吞吐 | DROID **15.33 fps/GPU** | 视觉 SLAM（3 replicas） |
| 训练吞吐 | 4 卡 **+20%** | 训练基建调度优化后 |
| 数据效率 | **96 条** | VLA 全量微调即跑通抓放 |
| 训练目标 | **10,000 卡时** | ≈ 8 卡 × 60 天 |
| 部署周期 | **33 ms** | RTC action chunk 执行周期 ≈ 30 Hz |
| 触觉精度 | **2.54 kPa** | 带噪输入 → 干净力图 RMSE |

四个关键比率值得记住：采集日产能 ~800 条决定下游一切规模；标注吞吐接近 **1:1**（1 小时视频 ≈ 1 小时 GPU 时间）曾是接单瓶颈；训练目标 10,000 卡时 ≈ 8 卡连跑 60 天；部署执行周期 33 ms ≈ 30 Hz 控制频率。

## 二、算力与平台基础设施

### 2.1 算力资源

- **H200 双节点自建**：node1 部署 LLM 服务，node2 按 1/2/4/8 卡切分 pod。
- **NAS**：2U 双路存储服务器（2 × Xeon，硬件 RAID，25GE × 2），16 TB × 32 ≈ **0.5 PB**。
- **网络**：200G + 25G 网卡、MPO-MPO OM4 光纤、国产 100G 光模块。**公网出口仅 50 M——这是最大瓶颈**。
- **评估过的方案**：国产 AI 加速卡（生态为 fork 版本，同价位性能不占优）被否决。

自建算力的经济学很直白：**一块 140 G 显存的卡如果只用了 15 G，或者干脆空闲 90%，等价于每天都在持续烧钱**。所有治理手段都围绕利用率展开。

### 2.2 自研 GPU 调度平台

- 自助创建 / 开关机 GPU pod，SSO 登录。
- 工作区隔离：标注实验、世界模型实验、VLA 微调、触觉实验、压测等各自独立。
- **利用率治理三板斧**：
  1. GPU pod **空闲 24 h 自动关机**；
  2. 关机前 **2 h 推送预警**；
  3. 每日定时日报（早晚各一次）。
- **利用率红线**：`50% pwr / 50% vram`。

这里的设计逻辑值得借鉴：**不靠人的自觉，靠自动化回收 + 公开日报形成的压力**。共享算力的最大成本从来不是硬件，而是「有人占着不用」。

### 2.3 三层存储

| 层级 | 用途 |
|---|---|
| 私有持久盘 | 个人工作区，长期保留 |
| 共享盘（mine / all） | 团队内部交换 |
| S3 对象存储 | 数据集与产物归档 |

对象存储经历过一次**全栈迁移**：从自建 RustFS 迁到 MinIO 全栈替换，**写冻结仅 16 分钟**，用 md5 锚点核验数据一致性。五个桶按用途划分（models / datasets / scratch 等）。

配套的 **key 管理 Bot**：

- 按 bucket 发放限时写权限；
- `datasets` 桶需审批；
- `scratch` 桶 30 天自动清理；
- 权限上限 720 h。

**踩坑记录**：ZFS 更换阵列卡后，32 盘聚合带宽掉到仅 400 MB/s（单盘 277 MB/s）——存储性能问题往往出在控制器层，而不是盘本身。

### 2.4 LLM 网关

- **Docker 蓝绿双容器部署** + 配置经 Git 管线同步，发布脚本分 `prepare` / `promote` 两阶段原子切换 + 自动回滚。
- **模型池**：以国产长上下文模型为主力池（11 个账号），配 Claude / GPT / GLM 的 **fallback 链**。
- **典型故障**：容器 `mem_limit` 2.4 G 导致 OOM → 扩容到 6 G，并引入 `resource-budgets.json` 作为**唯一事实源** + 校验脚本。

**核心原则**：单一事实源 + 自动化校验 + 原子发布。这个网关后来沉淀出完整的故障案例库（见第九节）。

## 三、数据采集：遥操作框架与动捕产线

### 3.1 采集规模与 KPI

- 累计 **713 个任务**（3 个 namespace），累计采集时长 **347,742 秒 ≈ 96.6 小时**。
- **履约率波动极大：2.0% ~ 96.5%**——难物体常常零产出。
- **28-DoF MANO 手型资产**，按操作员分别训练（不同操作者的手型差异需要单独建模）。

### 3.2 动捕系统

采用**光学与光惯双系统**并行：

| 系统 | 适用 | 采集频率 |
|---|---|---|
| 光学动捕 | 仅右手手套 | 100 Hz |
| 光惯动捕 | 双手手套 | 120 Hz → 统一 100 Hz |

**刚体规则**（细节决定数据可用性）：

- 刚体原点 = 反光点三维坐标的平均值；
- 物体限定 **3D 打印刚体**，钻孔埋 ø5 / 6 mm 反光球（常备 500 颗）；
- **铰接体按规则拆成多刚体**（例如「带盖瓶子」拆成「瓶体 + 盖子」）——否则单刚体无法描述相对运动；
- 纹理缺失的物体 → 3D 扫描调研 + **real2sim** 建模（实物转仿真资产，含摩擦参数）。

### 3.3 数据流水线

- 存储路径按项目分区，每日 00:00 cron 自动导出 + 按日增量写 **Lance**。
- 迁移到 S3 双站点（工厂侧 + 研发侧）统一 bucket。
- **处理协议演进**：`pre60` → `pre120` / `earlyPhase50` / `operator-matched+4000`——协议版本化是数据可复现的前提。
- **合成数据配比 1:5**（对 XY 施加 ±2 cm 扰动）。

### 3.4 痛点与整改

| 痛点 | 整改 |
|---|---|
| 反馈回路长达「cron 1 天 + 取用 N 天 + rollout 2 天」 | 要求压到 **10 分钟内**：采集侧提供 clean 版、异常实时反馈 |
| NAS 使用率 **97%**（误操作产生数 TB 重复目录） | 紧急清理 + 目录规约 |
| cylinder / cuboid 等细高易倒物体**履约率为 0** | 物理限制需从**任务设计**上规避，而不是硬采 |

**数据工厂的核心 KPI 不是总产量，而是履约率与反馈延迟。** 像「瓶体 / 盖子」这类多物体命名歧义、拇指原始数据异常这种小问题，会直接污染下游 RL 训练——所以**任务派发文档（任务描述 / 道具 / 流程 / 注意事项）是强制规范**。

## 四、Ego 自动标注管线

把海量第一视角（egocentric）视频全自动转成结构化数据：手部 6DoF / MANO 关键点 + 深度 + 相机位姿 + 语义标注，输出 JSON 并可 API 化对外服务。这是「数据飞轮」里最重的工程模块。

### 4.1 模型流水线

```
hand detect → wilor / hawor → UniDepth → DROID SLAM → Cosmos → JSON 出库
  YOLO+SAM     MANO 6DoF       单目深度     稠密对应/位姿   语义 caption    uuid 异步取回
               21 关键点      40fps@2×A800  15.33fps/GPU   区间化标注
```

**GPU 分配方案（8 × A800）**：2 卡 UniDepth + 2 卡 DROID + 1 卡 wilor + 1 卡 hawor + 2 卡 Cosmos + 1 卡手部检测。

### 4.2 服务架构

- **仓库拆两层**：推理层 + 编排层，解除语义耦合。
- 模型封装为**常驻 API**（Ray Serve），工作流引擎用 Hatchet（engine / dashboard / rabbitmq / postgres 四容器）。
- **任务以 uuid 异步取回结果，不用长连接**——直接避免 10 分钟连接超时。
- 鉴权 + nginx 反代 + 自签证书。
- 关键优化：**模型权重共享卷零拷贝**；GPU0 35.8 G（深度 + SLAM）、GPU1 128.2 G（位姿 + 世界模型）。
- **API 规范**：上传返回 uuid → 凭 uuid 取回 JSON、固定 schema、语义 caption 用 `(start, end, caption)` 区间化、**不在服务端渲染**（渲染交给脚本）。

### 4.3 并发治理

**问题**：3 个客户端并发打深度估计常驻服务 → 频繁 `503 unidepth_unavailable`。

**根因**：后端是竞态提交、没有队列——请求进来就抢 GPU，抢不到直接失败。

**方案**：

1. 每模块**排队**（Ray Serve 风格）；
2. **满 batch / 满等待即发车**（不空等）；
3. **admission control**——超出容量直接拒绝，而不是让它排队到超时。

这是典型的「把过载从雪崩变成排队」的工程手法：**负载不是被消除的，是被显式管理的。**

### 4.4 产能测算与商业决策

一次真实决策链：

- 接到 **1000 小时 @ 30 fps** 的标注订单；
- 测算：4 卡需要跑 1~2 个月，**吞吐比接近 1:1**（1 小时视频 ≈ 1 小时 GPU 时间）；
- **结论：拒单。**

拒单不是能力问题，是产能结构问题。后续路线是**用消费级显卡集群线性堆卡**（标注成本下降约半个数量级），把 H200 定位为训练卡。目标产能：**每周 1 万小时订单**。

> 这个决策的价值在于：**先算清楚 ROI，再决定接不接单**。吞吐 1:1 的业务，本质是在卖 GPU 时间，做不成规模化服务。

### 4.5 管线的两个经典坑

| 坑 | 现象 | 解法 |
|---|---|---|
| **深度尺度不一致** | 手部模型隐含深度与单目深度投影不重合 | 直接输出**关键点像素坐标**，摆脱逐帧深度依赖 |
| **语义标注失败拖垮全链路** | 结构化输出失败导致整条管线中断 | 语义标注不可忽略，必须**改后端**，不能跳过 |

## 五、训练基建：Tenon

Tenon（「榫」）是自研的 VLA 训练基础设施，命名取「榫卯咬合」之意——**模型微调 × 物理 AI**。架构是 mint-style 的 server / client 分离。

### 5.1 架构设计

- **Server（JAX 训练）+ 多 Client（供数）** 分离。
- **multi-LoRA + FSDP 切分天然适配**：不同 dp shard 加载不同 adapter——这是设计上最巧的一点，让「多任务 adapter」和「分布式训练」在同一个框架里成立。
- 基座为 Pi0.5（openpi 代码库）；早期用过 82 维 action 的验证性分支，经验已沉淀。

### 5.2 调度优化：把开销藏进计算

**问题**：原实现的 `exec_lock` 把「Host 侧数据准备」与「JAX 训练」串行包在同一临界区——GPU 在等 CPU 喂数据。

**优化结果**：

| 配置 | 优化前 | 优化后 |
|---|---|---|
| 单步平均吞吐 | — | **+6.41%** |
| 2 卡 | 50 | **60** |
| 4 卡 | 88 | **115**（16% → 20%） |

关键手法是**引入 pipeline depth**。公网验证数据很说明问题：**pipeline depth = 3 时，0.66 s 的网络上传几乎完全藏进 server 计算**，吞吐恢复到同机运行的 98%。

### 5.3 多卡规模化验证

4 × H200 验证配置：

- Global batch 128 / per-device 32，1,000 optimizer steps，**128,000 样本**；
- 数据为 120 Hz 原生采样、筛选出的高质量 cohort（1,452 行）；
- 采样策略 `sqrt_tempered`（slate 16）；Action 32 维、horizon 10、State 45 维。

**对标**：业内有团队用分布式缓存层加速对象存储读取，提速约 35%——说明数据供给是行业共同的瓶颈点。

### 5.4 Cosmos 世界模型微调

一条实验路线，目标是从 ego 视频做动作标注：

- 基模为 Cosmos 系列（nano / super）。
- 把官方 **57 维 ego action 扩展为 147 维 → 192 维**（相机 9 + 腕部 9 × 2 + 关键点 60 × 2）。
- **reasoner（自回归，监督语言）与 generator（扩散 flow matching，监督动作）分离 SFT**；inverse dynamics 模式下 guidance = 1。
- 决策：**搁置自回归路线，全力训扩散模型上规模**。814 windows 下 generator 误差 34 mm，腕部仍漂移（wrist loss 权重 5x / 10x 试验中）。
- 优化：视频处理从 CPU 移到 CUDA，nano 微调单卡峰值 34 GiB、效率 3.6~3.8 GPU-hour。

**训练基建的核心洞察**：**数据供给才是训练瓶颈**。base64 + JSON 的媒体传输路径曾占服务端 50% 耗时（202 MB 视频 → 270 MB payload，prepare 5.7 s > GPU generate 4.9 s）。优化方向不是换更快的 GPU，而是**消灭 CPU 侧数据准备与网络传输开销**。

## 六、VLA 训练：Pi0.5 微调主线

### 6.1 输入输出契约

- **输入**：RGB + State45 + tokenized prompt
- **输出**：Action32（32 步 action chunk）

两条微调线并行：真机数据线（全量微调）与 MANO 主线。

### 6.2 数据效率：96 条跑通抓放

**最反直觉的一个结果**：仅用 **96 条真机数据**做全量微调，就跑通了抓取—放置。

这说明 **VLA 微调的数据效率远高于从零训练**——预训练权重已经把「视觉—语言—动作」的对应关系学得足够好，微调只需要把动作空间对齐到具体本体。

### 6.3 泛化的边界：一个「屋顶」的差别

OOD 测试的翻车案例非常经典：

> 移动物体、移动手之后效果不明显。失败根因是——**训练与推理场景差了一个「屋顶」**：灯光条件变化 → 手的影子不合理 → 策略失效。

**本质是过拟合：场景扰动没做。** 泛化能力来自数据多样性，不是模型容量。所以后续动作是：

- **场景扰动系统化**；
- 一个物体配 **7 种抓取手势 ≈ 1000 条** diversity 数据，验证「任意位置出发」的成功率；
- 数据组织用命名规约（如 `cube1_01` = 物块 1 + 抓取指法 01 + 序号，30 条/组）；
- 自研可视化编辑器修轨迹，做手回撤 / 手指状态的平滑处理。

### 6.4 长期训练架构（定稿）

| 项 | 决策 |
|---|---|
| 微调方式 | **大 LoRA + 主干持续续训**，几乎不再从头开训 |
| 数据口径 | mid-train 需吃宽口径数据 |
| 资源 | 长期一台 **8 卡机专供基模训练** |
| 训练目标 | **10,000 卡时**（8 × 60 × 24），先跑 1000 |
| 产物 | **每日出新 checkpoint** |
| 回归 | **每日自动跑基准评测**，监控旧任务遗忘与训练爆炸 |

### 6.5 评测体系

| 评测对象 | 方法 | 意义 |
|---|---|---|
| 标准 pick & place | LIBERO 基准，**每日自动跑** | 监控遗忘与爆炸 |
| 灵巧手抓取 | 每个 `(object, gesture)` 组合测一遍成功率 | 自建基准的雏形 |
| 最终对外 benchmark | 专门刷分 | 品牌与论文支撑 |

### 6.6 长程任务的现实

- 论文里的 high-level 子任务拆解代码**实际上未实现**；
- 手工编排 sub-prompt 能拼出长程任务，但**「回撤后手停在新 state，下一动作不 work」**；
- 路线：**先自研语言 planner**，走通后再端到端。

这是具身智能里一个普遍的落差：**论文里的长程能力，工程上往往还是手工编排。**

## 七、小模型 RL：残差策略与 real-to-sim-to-real

### 7.1 管线

```
真人动捕 100 Hz ──▶ MANO retargeting ──▶ RL 残差策略训练 ──▶ Sim2Real ──▶ DexHand 真机
  光学/光惯动捕        映射到灵巧手关节      Isaac Gym → MuJoCo    r2s2r     抓放/掌内调姿/倒水
```

### 7.2 方法要点

- **residual policy（残差策略）**：在参考轨迹之上学习修正量，而不是从零学动作——这是把动捕先验用起来的关键设计。
- **FiLM 调制**实现通用策略：用 one-hot 的 manipulation primitive label 作为条件输入，一组权重覆盖多种操作原语。
- **unseen 动作**按「几指抓取」归类到相近 label，避免完全失效。
- **奖励设计**：以 `follow object pose` 为主；接触 reward 按「关节—物体表面距离」调制；偶发丢帧可忽略。
- **训练规模**：289 / 290 条动捕数据**全量训练**；另有 1,595 条合成轨迹可用。

### 7.3 关键决策

| 决策 | 内容 |
|---|---|
| **仿真器迁移** | Isaac Gym **退役**（仅历史原因在用），论文结束后主线迁 **MuJoCo** |
| **状态输入（定案）** | current frame + 12 点云、特权信息（参考误差 / 速度误差）、16 关节接触信息；**不用关节速度** |
| **一次误识别** | 任务号被误识别成 primitive label → 期望关节配置全错 → 多物体轨迹默认双手末端 5 关节 → **弃用 one-hot** |
| 对比基线 | 与两种主流 retargeting 基线相比吞吐优势不大，论文不强调 |

**路线图**：RL 双线并行（一条做 waypoint 引导的泛化策略，一条改进残差策略：特权观测、点云 cross attention、掌内调姿），目标是**合并为统一 policy，再喂给 VLA 做后训练**。

## 八、真机部署与 sim2real

部署是技术栈里**最深**的一环：问题一半在算法之外——真机故障记录里出现过「左手两指异常」「右手过热损坏」「灵巧手连不上」「双目相机失联」。

### 8.1 实时部署参数

- **RTC（Real-Time Chunking）**：动作按 chunk 下发，执行周期 **33 ms**。强行执行 N 倍 chunk 可以提速，但**过渡段会抖动**。
- **关节限速 0.315 rad/step + temporal ensemble**。
- **抖动根因不是缺 ensemble**，而是 **chunk 过渡 + retargeting 的「接触帧 → 非接触帧」跳变**。
- **RL 控制频率 100 Hz**（仿真步长默认 0.01 s）。
- **一个经典教训**：**不要把仿真步长当速度旋钮**。曾经为了让策略「跑得快一点」调大仿真步长，结果现实按 0.02 s 走、策略只按 0.01 s 走——速度没变，误差翻倍。
- **延迟测量方法**：用正弦波高频指令，分别测「策略 → 执行器」与「传感器 → 策略」的**双向延迟**。

### 8.2 sim2real 差距

**最典型的 gap**：某代灵巧手的触觉固件发 **30 个数字，但物理点只有 24 个**——仿真里的触觉观测量**没有实际物理含义**。

**Teacher-Student 两套方案**：

1. 已训策略做教师，保留全观测；学生砍掉真机上没有的观测后重训；
2. critic 用仿真观测、actor 只给真机观测。

**物理量三级处理**（这条原则非常实用）：

| 类型 | 处理方式 |
|---|---|
| 手工标定准确的 | 直接用，**上苦力不上算法** |
| 只能测个大概的 | 加 randomization |
| 测不出来的 | 在 student 里**删掉** |

### 8.3 感知与标定

- **手眼标定**：AprilTag 贴码到手背。
- **物体位姿**：FoundationPose。
- **问题**：FoundationPose 在动态位姿下不准（手物遮挡）→ 退回传统视觉 / 滤波方案；真值采集需要额外的动捕相机并再做一次手眼标定。
- 30 fps 头部相机存在**残影**问题；双目相机偶发连接故障。

### 8.4 结论性认识

**VLA 动作慢，根因在数据源头**——遥操作采集时人本身就是慢的。部署侧调参只能缓解，**提速必须回到采集阶段**。

## 九、Dexathlon：自研评估基准

「Decathlon = 十项全能」，定位是**多项全能操作能力评测**，前身是数采任务的 benchmark 仓库体系，目标服务数据工厂的规模化采集与模型对比。

### 9.1 任务设计

- **原子动作集**（首批 **21 个动作**）→ 排列组合 scale up；另加 **5~10 种双手任务**。
- 任务脑洞很有意思：双手拧哮喘喷雾、单手开口香糖瓶、AirPods 单手取耳机、手表单手佩戴、薄卡片刷卡。
- **超长程任务**：书架最高层取台灯 → 插电 → 展开 → 按钮启动 → 调光照。
- 参考：LIBERO（一百多环境全采）、RoboTwin、RoboDojo。

### 9.2 评估协议

- **「环境 ×（本体 + 模型）」矩阵打分**，自动化打分工具。
- 每套任务采 **10 条**（A 放 B、B 放 A、前后左右各位置）。
- **指标**：成功率 + 重定向评测的**穿模频率、接触还原度、吞吐**。

### 9.3 资产体系

- **仿真器**：MuJoCo；场景由自研场景生成 skill 产出（`scene_library` 六级结构，319 MB）。
- **物体 / 手资产**：1.2 G（STL 117 个 + OBJ 475 个）；MANO 蒙皮手。
- 数据统一入库 `s3://.../dexhand_benchmark/`。

**基准的护城河在「资产与真机的对齐工艺」**：

- STL 与光学动捕刚体坐标对齐，靠**钻孔孔洞与 JSON 反光点匹配**；
- 剪刀刀片太薄无法挖孔 → 改用「ø5 mm 凸点 + 2 mm 反光贴」方案；
- 打印件孔位规则已冻结标准化。

## 十、触觉映射：从电压读数到力图

### 10.1 硬件现实

某代灵巧手每指尖固件提供 **30 维电压读数**，但**物理点仅 24 个**，且**无出厂力标定**。

### 10.2 映射方案

```
6D 力 [Fx,Fy,Fz,x,y,z] → mesh → 球面 → plate → UV → 128×128×3 力图
                                                          │
                            jacobian 面积加权 ◀───────────┤
               扩散参数 sigma + 材料系数 C 随机化 ◀────────┤
                     噪声取 p1 峰值 10%（数据生成环节注入） │
                                                          ▼
                                              64 维 latent（输入 arctan 预处理）
```

- **loss 对比**：MSE vs MSE + 法向峰值约束。
- **数据构成**：两类传感器 1:1 混合；**单接触 : 多接触 = 4:1**（多接触尚无法恢复）。
- **生成成本**：200k 样本单核 3 小时。

### 10.3 精度指标体系

| 评测路径 | RMSE (kPa) | 解读 |
|---|---|---|
| 带噪输入 → 干净力图 | **2.54** | 模型去噪能力，接近传感器理论下限 |
| 干净输入 → 重建 | **12.48** | 编码—解码往返误差 |
| 带噪输入 → 重建 | **12.51** | 端到端误差主要来自**重建**而非噪声 |

**结论**：端到端误差的瓶颈在表示重建，不在输入噪声。所以优化方向应该是提升 latent 表示能力，而不是继续加去噪。

**路线选择**：在 `tactile-free` / `binary tactile` / `tactile mapping` 三种方案中对比验证。**触觉不是「有没有」的问题，而是「多准确的触觉才值得增加部署复杂度」的问题。**

## 十一、LLM 网关：可靠性工程实录

内部 LLM 网关（LiteLLM）在两个月内沉淀出完整的「报错 → 根因 → 修复」案例库，由运维 Bot 按生产门禁规则自动分诊。**写操作需回复编号确认，调查挂 session 链接，产出 case 档案。**

### 11.1 架构

- LiteLLM 网关（Docker 蓝绿双容器）+ `state.json` 记录 activeCommit + 自动回滚。
- **请求载荷存对象存储冷存**（DB 只存编号 / 模型 / 状态 / 耗时）——避免大 payload 拖垮数据库。
- 模型池：国产长上下文模型为主力（11 账号）；fallback 链如 `claude-opus → [claude-sonnet, kimi]`。

### 11.2 故障案例 Top 6

| 故障 | 根因 | 修复 |
|---|---|---|
| 新模型 400：从未 onboarding | 修复 PR 卡在三项人工门禁 | 临时降级到旧版本 |
| thinking block 签名 400 | 客户端回放损坏的签名 | 新会话规避 |
| fallback 模型全灭 | 上游只认**字符串** `reasoning_effort`，网关透传了**对象** | 触发 2 strikes → 300 s cooldown → 加 overlay 做类型转换 |
| 403 雪崩（185 次） | **账期耗尽 36 次 + 并发超限 68 次** | 专用并发信号量 + cooldown 从 300 s 灰度降到 60 s |
| 524 超时 | 主节点队列上限 100、等名额 30 s → 源站 2 分钟无响应 | 调队列与超时策略 |
| 容器 OOM | `mem_limit` 2.5 G 不足，热修复曾成**孤儿提交** | 扩到 6 G + `resource-budgets.json` 唯一事实源 |

### 11.3 共性根因

**几乎所有故障都源于「配置多源不一致」**：Git 管线遗漏、孤儿提交、人工门禁卡壳、类型透传错误。

解法都指向同一原则：**单一事实源 + 自动化校验 + 原子发布**。

## 十二、总结：六条工程原则

1. **数据供给是训练瓶颈，不是 GPU。** 当 prepare 耗时 5.7 s > GPU 计算 4.9 s 时，优化对象是数据管道，不是硬件。
2. **泛化来自数据多样性，不是模型容量。** 一个「屋顶」的差别就能让 VLA 翻车——场景扰动必须系统化。
3. **过载要显式管理，不要让它雪崩。** 排队 + 满批即发 + admission control，把 503 变成可控的等待。
4. **仿真步长不是速度旋钮。** 所有「调个参数让它快一点」的捷径，最后都会以 sim2real 误差的形式还回来。
5. **物理量的处理要分级。** 标定准的直接用，测得糙的加随机化，测不出的删掉——不要用算法去补不存在的信息。
6. **基建的可靠性来自单一事实源。** 配置多源必然不一致，不一致必然出事。
